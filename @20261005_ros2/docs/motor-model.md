# 电机模型：MIT 公式与非理想项（仿真侧）

这篇讲**仿真侧那台"电机"**（[`include/quadruped_ros2/motor.hpp`](../ws/src/quadruped_ros2/include/quadruped_ros2/motor.hpp)）在算什么、参数怎么调、以及非理想项实测起了多大作用。任务分工、话题接口与参数全表见 [`ros2-nodes.md`](ros2-nodes.md)。

## 1 为什么非理想项放在仿真侧

实机上跑 MIT 五参数的链路是：**上层控制器**（我们写的 `controller_node`）→ 总线 → **驱动板**（FOC 电流环 + 编码器）→ 电机。死区、电流限幅、指令延迟、噪声都发生在**驱动板与电机**这一侧，上层控制器**看不见**也管不着（讲义 §1.1）。所以在仿真里它们属于"机器人/电机"那一侧，也就是本节点（`sim_node`）——**控制器代码一行都不用改**，换一组参数就等于换一台电机。

## 2 理想部分：一条公式 + 一道限幅

关节侧（输出端）的 MIT 混合控制：

```
τ = τ_ff + kp·(q_des − q) + kd·(w_des − q̇)     然后 clamp(τ, ±tau_max)
```

`{τ_ff, kp, q_des, kd, w_des}` 就是 `/mit_command` 的五个字段；本模型的执行器是 `<motor gear="1">`，所以 `data.ctrl` 直接就是关节侧力矩。`tau_max` 默认取模型 `ctrlrange`（±20 N·m，可用参数 `tau_max` 覆盖成实机的 33.5）。这一部分在代码里是纯函数 `motor::Torque()`，**与算法、控制器、实机用的是同一条公式、同一组值**。

## 3 非理想部分：四个开关（默认全关 = 理想力矩源）

| 参数 | 默认 | 含义 | 量纲 |
|---|---|---|---|
| `motor_deadzone` | `0.0` | **静摩擦死区**：`0 < \|τ\| < 死区` 时输出 0（小力矩推不动） | N·m |
| `motor_delay_cycles` | `0` | **指令延迟**：用 N 个**控制周期之前**下发的那条指令（反馈仍是当前值） | 周期（500 Hz 下 1 周期 = 2 ms） |
| `motor_noise` | `0.0` | **力矩噪声**（高斯白噪声，加在限幅之后） | N·m（标准差） |
| `motor_seed` | `12345` | 噪声种子：同参数 + 同 seed → **同一条噪声序列**，回归可复现 | — |

语义与计数口径**照搬第三次培训的完整版**（`@20260927_motor/cpp/src/motor.h` 的 `JointMotors`），这样两个任务的数字可以直接对比。三个容易写错的地方（前两个是完整版踩过的坑）：

* **`τ` 正好是 0 不算"落死区"**：阻尼模式下狗停稳后 `q̇ = 0 ⇒ τ = 0`，若把 0 也算进去，5 s 仿真能报出上万次假计数。只有**真的被削掉**（`0 < |τ| < 死区`）才计数；
* **`dead_events` 才是"进出死区几次"**：`dead` 是**电机·步**（采样点），一次穿越在死区里停 10 步就记 10；
* **延迟必须"每步推进一次历史"**：`Bank::Apply()` 是**每步调用一次**的接口。若按关节调用（12 次/步），N 周期延迟会变成 N/12 周期——`Bank` 的注释里写明了这条约束；
* 噪声加在**限幅之后**（完整版同序），所以输出可以略微超过 `tau_max`，这是刻意的（量纲上是力矩纹波），别"顺手修掉"。

`Bank` 在全关时**直接走理想公式**（`motor::Torque()`），因此"不引入非理想项"的回归结果与改动前**逐位一致**（自检第 1 项就在钉这件事）。

## 5 端到端实测：狗还站得住吗

同一条链路（`sim_node` + `controller_node` + 手柄序列按 A 起身），10~20 s：

| 参数组 | 站姿结果 | 电机统计 |
|---|---|---|
| 温和：`0.05 / 1 / 0.05`（死区/延迟/噪声） | z=0.3836 m、tilt 0.0°、`ncon=4` ✓ | — |
| **典型（完整版实测用的那组）：`0.5 / 2 / 0.2`** | z=0.3836 → **0.3837 m**、tilt ≤ 0.1°、`ncon=4` ✓ | 累计 114300 电机·步，**撞限幅 0 次**，落死区 **72869 电机·步（63.8%）**、进出死区 3554 次，\|τ\| 峰值 10.87、均值 1.38 N·m |

结论：这组"真实参数"确实在咬（63.8% 的小力矩被死区吞掉，与完整版同量级实测的 53.7% 对得上），但**站姿只被扰动到 0.1 mm / 0.1° 量级**——说明当前站姿控制对这些非理想项是**鲁棒**的，退化是渐进的而不是"一开就散"。要更狠的验证就加大死区/延迟（例如 `motor_deadzone:=2.0`）看它什么时候晃起来。

复现（典型组，可复现同一条噪声序列）：

```bash
pixi run ros2 launch quadruped_ros2 bringup.launch.py motor_deadzone:=0.5 motor_delay_cycles:=2 motor_noise:=0.2
# 或只跑节点（统计行在退出时打）：
pixi run ros2 run quadruped_ros2 sim_node --ros-args -p viewer:=false -p status_period_s:=0.5 \
  -p motor_deadzone:=0.5 -p motor_delay_cycles:=2 -p motor_noise:=0.2
```

## 6 明确**没建**的项（以及理由）

* **转子侧电气量（电流、电压、反电动势降矩）**：需要电机电气模型 + 实测标定数据，本任务没有；`MotorState.cur` 因此一律报 0（理由见 [`ros2-nodes.md`](ros2-nodes.md) 的决策 3）。
* **编码器量化 / 采样抖动**：完整版没有这项，本任务保持一致（噪声只建了力矩噪声这一项）。
* **真·静摩擦（粘住不动）**：`data.ctrl` 只能施力、不能施加"约束"，所以死区只能做成"小力矩被吞掉"的近似；MuJoCo 里物理上更正确的位置是模型字段 `dof_frictionloss`（属于"机器人"而不是"电机"）。要更硬核的静摩擦可以后续在场景 XML 里加 `frictionloss`，与这里的死区组合使用。
