## 1 硬件现状（2026-09-27 实测）

| 项目 | 实测结果 |
|---|---|
| USB 转接芯片 | **FTDI FT232H**（`0403:6014`，"USB <-> Serial Converter"，SN `FT7YS34D`），USB 2.0 **High Speed**、单通道、bulk 端点 512 B ⇒ 芯片本身最高 **12 Mbaud**，SDK 要的 4 Mbaud 在能力范围内 |
| 内核驱动 | `ftdi_sio`（`usbserial` 系列）**自动绑定**，内核自带 ⇒ **不需要再装任何驱动/编译模块** |
| 设备节点 | `/dev/ttyUSB0`（`crw-rw---- root:dialout`） |
| 权限 | 当前用户 `bis` **不在 `dialout` 组** ⇒ 现在必须 `sudo`，或者 `sudo usermod -aG dialout bis` 后**重新登录** |
| 供电 | 该设备描述符声明 `MaxPower 100mA` —— USB **只供通信**，电机必须外部供电（任务书：大疆电池） |

`serial_probe` 的"端口探针"会打印这个端口能不能配成 SDK 要的参数（`TIOCGSERIAL` 的
`baud_base`/`custom_divisor`）——**这项已经实测通过**（S0，见下表）：

| S0 结果（2026-09-27，`sudo /tmp/serial_probe --port /dev/ttyUSB0`） | 读数 | 含义 |
|---|---|---|
| `tcgetattr` | 打开前是 `B9600`（未配置时的默认值） | 正常；SDK 构造后会改掉 |
| `TIOCGSERIAL` | OK，`type=0`、**`baud_base=60000000`**、`custom_divisor=0` | FT232H 在 HS 模式下基频 60 MHz |
| 4 Mbaud 的除数 | `60000000 / 4000000 = 15.000` **整除** | 4 Mbaud 可以**精确**配出，不会有波特率误差 |
| `SerialPort` 构造 | 成功（`/dev/ttyUSB0`） | SDK 要的 `TIOCGSERIAL/TIOCSSERIAL` 这条路径在这个转接头上可用 ⇒ **转接头选对了** |

## 2 我们的"电机驱动"成熟到哪了

"仿真里那套电机模型能不能证明实机可用"——分开看：**能复用的是"报文与换算"这一层，它已经被证明是对的；
不能复用的是"传输/标定/安全"这三层，它们还没写**。

| 层 | 内容 | 状态 | 依据 / 差距 |
|---|---|---|---|
| 数学 | 关节侧 MIT 公式 | ✅ 仿真里实现并实测（§sim.md 2.1） | 实机不需要这段（驱动板里跑的就是它），实机需要的是**换算** |
| 换算 | `ToRotor`：Pos/W ×N、tau ÷N、K_P/K_W ÷N² | ✅ 与官方 SDK 实际报文**逐字段对上** | 3.165 rad → `pos_des=16506`、K_P=1.9966 → `k_pos=2555` |
| 协议 | 报文字段与 CRC | ✅ 实测：`fe ee` + mode + 12 B + `crc_ccitt`(前 15 B) | 我们本地重算的 CRC 与报文完全一致 |
| 标度 | pos/speed/torque/gain 的定点标度、截断、32766 钳位 | ✅ 实测（[`../README.md`](../README.md) §4） | 含"速度是 q7 的 π 倍""增益超量程被静默截断"两个坑 |
| 反馈 | 读回 q/dq/tau/temp/merror 并转成关节侧 | ✅ 假电机的回帧被官方 .so 正确解出 | 实机同样路径，只差真链路 |
| 传输 | 真串口 4 Mbaud、半双工收发、时序/抖动、断线重连 | ✅ **已由 S1 实测** | 6 次 × 1601 帧、0 丢帧 0 超时、真的 4 Mbaud（§3.6）；**断链行为已实测**（S2e，2026-09-29）：驱动板**不会卸力**——上位机不发命令后它继续执行最后一条指令 |
| 标定 | `offset` 零点标定、零点跳变（±1/6.33 圈）检测与修正 | 🔧 **程序已就绪 + dry run 已跑通**（[`../apps/motor_ctl.cpp`](../apps/motor_ctl.cpp)）：`q = q_enc + offset`、`cmd.q = (q_des − offset)·N`、整数 raw 差判跳变；但**实机还没标过** | 约定见 §5、手册见 §3.8、dry run 证据见 §3.8 末尾；实机剩下的是"这颗板子的读数到底是里程计还是锯齿"（S2b）与"上电基准会不会变"（S2f） |
| 安全 | 看门狗（收不到回复就卸力）、斜率/速度/力矩限制、温度与错误处理 | 🔧 `motor_ctl` 已有：梯形插值（vmax/amax）、到位保持、连续 40 帧无回复 → 零力矩退出、`merror`/温度退出、力矩持续超限判卡住。**S2e 已证明驱动板不会自己卸力**（它保持最后一条指令）⇒ 我们这边"退出前必发零力矩"是**唯一**的停止手段；程序被强杀（Ctrl-C/超时）时电机不会停，要么用本仓库程序的收尾逻辑，要么断电 | `spin_test`/`serial_probe` 也会查温度/`merror`/连续超时并带斜坡 |

一句话结论：**“链路（S1） + 报文 + 换算 + 标度”已经有实机实测支撑**，但“零点标定/跳变处理”与“安全限幅”
还只是有方案、没上过実机，所以还不能叫“成熟的实机驱动”。可复用的代码是 `cpp/src/motor.h` 里的
`Cmd` / `RotorCmd` / `ToRotor()` / `RotorToJointAngle()`（拿过来当实机程序的换算核心）
⚠️ 子任务项一正在拆分（`cpp/src` 完整版 / `cpp/essential` 最简版），拿代码时以**当次**的目录为准。

| **S5** 零点跳变处理（任务书 4；**重点是上电那一次**，见 [`zero_semantics.md`](zero_semantics.md) §1–§2） | **程序已就绪**（同上；执行卡 runbook §4 批次 6）：手动把输出端越过零点（前后各试），程序用**整数 raw 差 ≈ k×32768**（k 个转子圈 = k×56.842° 输出端）判“跳变”，检测到就**只把 `offset` 反向补 k 个区间**（`q_des` 不动 ⇒ 同一个 `q_des` 仍对应同一个物理位置）；dry run 用 `--fake-jump-frame/--fake-sawtooth/--fake-datum-turns` 注入过三种情形 | 能报出“零点跳变 +k 个区间”并自动修正；修正后目标角仍对得上；手转到零点前后都不会"跳走" | 阈值（默认残差容差 8°）要远大于“正常转速上限 × 真实帧周期”（§3.6 实测 5.585 ms/帧），又要远小于半个区间（28.4°）；**跳变那一帧驱动板自己会抡一下**（我们只能事后救），先低速试；不要与"正常越过零点区间"搞混（§5） |

把"假电机"从固定回帧升级成**一阶速度响应 + 库仑摩擦 + 力矩限幅**的小模型（已写：
[`../include/motor_bench/sim/fake_motor.hpp`](../include/motor_bench/sim/fake_motor.hpp)，`--self-test` 就是用它；报文与标度全按实测值收发），
S3–S5 的控制与标定逻辑就可以**先在 dry run 上跑通**，再上实机——这样实机时间只花在真正需要实机的事上。
它的层级/接口/时序/保真度边界单独成文：[`fake_motor.md`](fake_motor.md)（"仿真电机"是怎么向官方 SDK
伪装成一台真电机的）。

顺手能学的两件事：

* 假电机的 `tau_fric` 调到 0.02 N·m（转子侧）时，速度环会出现 **稳态误差 = `tau_fric / K_W`**
  （0.02/0.0125 = 1.6 rad/s 转子 ⇒ 输出端 0.25 圈/s）—— 这就是实机上"速度模式给不到目标转速"的原因；
* 所以 S2 可以顺便量**真实的速度环稳态误差**（同一条 `dq` 指令下的实测转速 vs 指令），
  它就是"这台电机的摩擦/阻尼比"的直接体现，也是后面判断零点标定精度的参照。

### 3.5 S1 上手手册（实机让电机转起来）

程序：[`../apps/spin_test.cpp`](../apps/spin_test.cpp)。与官方例程的区别是它**有斜坡、有上限、
有错误处理**（官方例程是 `dq = -6.28·N` 转子侧 = 输出端 1 圈/s 一直转、`while(true)`、Ctrl-C 后不管）。

```bash
cd ..            # 仓库根目录；一次性建好（顺带生成 compile_commands.json，见 ../../cpp_part2/README.md §0）
pixi run cmake -S @20260927_motor/cpp_part2 -B @20260927_motor/cpp_part2/build && \
    pixi run cmake --build @20260927_motor/cpp_part2/build
B=@20260927_motor/cpp_part2/build/spin_test
$B --rev-per-s 0.1 --ramp 2 --hold 3 --no-send        # ① 先看"将要下发什么"，不发字节
sudo $B --port /dev/ttyUSB0 --id 0 --rev-per-s 0.1 --ramp 2 --hold 3     # ② 真发（要 sudo）
```

**电机会收到什么**（`--no-send` 会原样打印，下面就是默认 0.1 圈/s 那次的实际输出）：

```
模式：FOC（速度模式：T=0、Pos=0、K_P=0、W≠0、K_W>0）
cmd.id=0、cmd.kp=0、cmd.kd=0.012479（输出端 0.5 ÷ N²）、cmd.tau=0、cmd.q=0
cmd.dq = 0 → 3.9773 rad/s（转子）；输出端 0.1 圈/s = 36 °/s（方向正）
报文：head=fe ee、mode=0x10、tor_des=0、spd_des=162、pos_des=0、k_pos=0、k_spd=15、CRC16
时序：2 s 升速（smoothstep）→ 3 s 匀速 → 2 s 降回 0 → 再发 1 s 零速度后退出（共 8 s，200 Hz）
```

**状态怎么变**：发之前电机是自由的（无通信）；第一帧之后进入 FOC 速度环（`K_W>0` ⇒ 像阻尼器），
升速期间缓慢加速到 36 °/s 输出，中段匀速，随后缓慢停下，最后 1.5 s 保持零速度。
退出后驱动板会怎样：**已实测（S2e，2026-09-29）——不卸力**，它会继续执行最后一条指令；
所以"停"只能靠自己发零速度/零力矩，或断电。

**每帧都是同一套值**（只有 `spd_des` 随斜坡变），出错时：`merror≠0` 或温度 ≥ 80 °C 会立刻收速度退出（码 4）；
连续 20 帧无回复退出（码 5）；一帧都没收到退出（码 3）。

| 6 | 1.0 圈/s | 1.005 圈/s | 100.5% | 0.94 圈/s | 1601 / 0 | 31 °C | 0 |

（"达成"下面那列是同一个量用 `data.dq` 读出来的值，两者之差就是"速度反馈准不准"。）

* **链路很稳**：6 次各 1601 帧，**0 丢帧、0 超时**（200 Hz 名义频率、4 Mbaud），温度 30–31 °C 不变，`merror` 始终 0。
* **方向**：正的 `cmd.dq` ⇒ 看着输出端盘，**转子与输出端都逆时针**（你的观察）。注意方向是**接线 + 极对**决定的，换线会反过来，靠这个记录不用猜。
* **位置读数跨次连续**：32.68° → 141.44° → 452.48° → 2444.57° → …（每次接着上次停的地方）⇒ 只要驱动板不断电，
  多圈位置就一直累计（转子侧已经到 148 圈）。**这对 S3–S5 是好事**：`data.q` 可以直接当"关节角度"，不用每次重新标零。
* 退出后：程序在结尾补发零速度指令，你观察到"正常停下并保持"。注意这里的"保持"是**摩擦**在保持
  （`kp=0`，没有主动位置环，用手能拨动）；**断链之后驱动板继续执行最后一条指令（S2e 实测，2026-09-29）**，
  S3 要主动测一次（关程序/拔线看电机状态），因为"插值到位后保持角度"要靠这个前提。

**两个这次才量出来的坑**（都已固化进程序）：

1. **名义 5 ms 一帧，实际是 5.585 ms**（`usleep(5000)` + 收发 + 调度 ⇒ 实际约 179 Hz，不是 200 Hz）。
   所以"按帧号 × 5 ms"当时间轴去算转速会**高估 12%**——我第一轮就是这么算的，把 1 圈/s 算成了 1.12，
   才会出现"112%"这种怪数。现在 `spin_test` 会打印**真实帧周期**，并用**墙钟 + 位置**算匀速段速度，
   以后看那两行即可（上表用的就是修正后的值；修正后 1 圈/s = 100.5%，与你用标志物量的一致）。
2. **`data.dq`（速度反馈）不能直接当转速用**：同一段里抖 ±8%，而且系统性偏低（上表：1 圈/s 时读 0.94）。
   以后**用 `data.q` 差分算速度**（int32 q15 的分辨率足够），或者自己给 `dq` 做低通。

**还没解释的一件事（留给 S2）**：低转速下有一个约 **0.034 圈/s 的绝对误差**（0.1 → 0.066、0.2 → 0.166；
09-29 那次是 0.040 / 0.042 圈/s ⇒ 反推 τ_fric ≈ 0.12–0.13 N·m 输出端，见下面 §3.6 续），
而 1 圈/s 时几乎没有。若它是库仑摩擦造成的，这个绝对误差应该**与目标转速无关**（≈0.034 圈/s ⇒
输出端力矩 τ ≈ kd_out × 误差 = 0.5 × 0.214 rad/s ≈ 0.107 N·m ≈ 转子侧 0.017 N·m）；1 圈/s 时看不到这么大的
误差，说明**还有别的因素**（例如驱动板对 `spd_des` 的解释与 SDK 的 128/π 不完全一致，或高速时阻尼占比变了）。
一次 **kd 扫描就能分开**：同一个目标转速（0.5 圈/s）取 `--kd-out 0.25 / 0.5 / 1.0 / 2.0`——

* 稳态误差 ∝ 1/kd ⇒ 是**库仑摩擦**（用斜率直接反推 τ_fric）；
* 稳态误差与 kd 无关 ⇒ 是**标度/系统性偏差**。

### 3.7 S2 上手手册（零力矩找零点 + 把两种误差分开 + 量断链行为）

S2 要回答的四个问题：① 手转时读数到底长什么样（**里程计**还是**只报相对最近零点**）？
② 记号笔那个点在读数上是几度？③ 跨越零点时会跳一个区间（56.842°）吗？④ 低速那个 0.034 圈/s 的误差是摩擦还是标度？
再加一个 S3 的前提题：⑤ **掉线后驱动板是保持还是卸力**？

**S2a 零力矩手转（工具：[`../apps/serial_probe.cpp`](../apps/serial_probe.cpp)）**

```bash
cd ..   # 仓库根目录
B=@20260927_motor/cpp_part2/build/serial_probe
sudo $B --port /dev/ttyUSB0 --id 0 --watch 60 --every 1 --log /tmp/s2.log
```

**电机会收到什么**：FOC 模式下**五个命令量全 0** 的帧（`tor_des=0 spd_des=0 pos_des=0 k_pos=0 k_spd=0`；“零力矩”就是讲义 §1.3 说的那行），
所以输出端是**自由的**（用手能拨动，只剩齿轮/轴承摩擦）；状态变化：第一帧之后驱动板进入 FOC 零力矩并一直保持，
我们只读 `q/dq/tau/temp/merror`，不会让它自己转。

**手转慢一点**：200 Hz 下一帧最多只能“正常”转 2°（= 400°/s 输出 ≈ 1 圈/s），甩手会比这快 ⇒ 误报。
建议：先**同方向慢慢转 2–3 圈**（= 12–19 个零点区间），再**反向转半圈**，中间停一停；
每到“记号笔那个位置”就**按一下回车**（先打几个字再回车就能给标记起名）。

**看终端上的两个东西**：每行都写着 `输出端角度（第 k 区、区内 x°）Δ`：

* `区内` 那个数在转一圈的过程中**反复回到 0** ⇒ 只报“相对最近零点”；
* `第 k 区` 一直变大/变小、Δ 一直同号 ⇒ **里程计**（S1 实测是这种）。

**S2b 分析**：`pixi run python @20260927_motor/scripts/agent_scripts/analyse_watch_log.py /tmp/s2.log`
会打印：帧数/实际频率、净位移（换算成“几个零点区间”）、手转量、每帧步进 max、**形态判定**、
≈±1 个区间的步进清单、每个 MARK 的读数（S4 标定直接靠它）。

**S2c 往返跨零点**：把上面那段里“反向”那部分单独看。反向也连续、且没有整间隔跳变 ⇒ 里程计可逆；
若反向（或任何时刻）出现 ≈1 个区间（56.842°，容差 10%）的步进 ⇒ 就是讲义 §2.6 的“认错零点”，
先记下来，S5 里用“`offset` ± 一个区间”处理。

**S2d kd 扫描（把低速误差分开）**（工具：[`../apps/spin_test.cpp`](../apps/spin_test.cpp)）

```bash
B=@20260927_motor/cpp_part2/build/spin_test
for k in 0.25 0.5 1.0 2.0; do
  sudo $B --port /dev/ttyUSB0 --id 0 --rev-per-s 0.5 --kd-out $k --ramp 2 --hold 4 | tee /tmp/kd_$k.log
done
for f in /tmp/kd_*.log; do pixi run python @20260927_motor/scripts/agent_scripts/analyse_spin_log.py $f; done
```

判据（§3.6 末尾）：稳态误差 ∝ 1/kd ⇒ **库仑摩擦**（用斜率直接反推 `tau_fric`）；与 kd 无关 ⇒ **标度/系统性偏差**。

**S2e 断链行为（S3 的前提，务必先测）**

```bash
sudo $B --port /dev/ttyUSB0 --id 0 --rev-per-s 0.1 --kd-out 0.5 --ramp 1 --hold 30 --drop-after 4
```

`--drop-after` 到点后**不再发任何字节、直接退出**（等价于线断/程序被杀，退出码 7）。观察：

* 电机**继续保持那个转速** ⇒ 驱动板会保留最后一条指令 ⇒ S3 的“到位后保持角度”全靠我们继续发帧，
  代码里必须有看门狗（我们自己不发 = 没人卸力）；
* 电机**自己停下/变松** ⇒ 驱动板有失联保护，S3 省一半事。

> **✅ 实测结论（2026-09-29，批次 1）**：**不会卸力**——`spin_test --drop-after` 之后电机仍按最后一条指令继续转
> （与"正常收尾会停"形成对比：那是程序自己补发了零速度）；**断电再上电后保持停止**（上电默认不自转）。
> 推论：① 我们的程序"退出前必发零力矩"是唯一的停止手段；② 被强杀（Ctrl-C / `timeout`）时电机不会停
> ⇒ 现场要留一个"停止"命令在手边（见 [`runbook.md`](runbook.md) §2 的 `STOP`）。

量完再用“拔 USB 线”复现一遍（更彻底）。**这一步请把电机固定好、手随时能断电。**

**S2f 上电基准 / 掉电重上电（任务书第 3 条要求"上电前先自己确定零点未跳变"，就靠这一步给判据）**

S2a–S2e 里没有一项能回答"这颗板子的基准会不会变"。做法（不额外写程序）：

1. 把输出端停在一个能重复的位置（记号笔那个点最好），`serial_probe --watch` 跑 1 s 记下读数（或直接抄
   `motor_ctl` 启动时打印的 `q_enc`）；
2. **断电再上电**（大疆电池开关；串口可以连着），电机不动，再读一次；
3. 重复 3–5 次，比较同一物理位置的读数：
   * 每次都一样（到 1 LSB 级）⇒ 基准是固定的编码器零点，"认错零点"只在**上电位置贴近零点边界**时才会发生
     ⇒ S4 的 `offset` 可以跨会话存档，上电用 `--expect-deg` 对一下就行（这也是讲义 §2.6 的例子）；
   * 读数差 ≈ k×360°（转子）= k×56.842°（输出端）⇒ 上电分支会变 ⇒ `offset` 只在**会话内**有效，
     每次上电都要检查并用 `fix`（或 `o±56.842`）补一个区间；
   * 读数每次都落在 0…56.842° 之外 ⇒ 说明"上电从 0 起累计"的模型不对，S2b 的结论要重写。
4. 顺便量一下"离零点边界多近会认错"：把输出端停在边界两侧 ±(0.5…5)° 各上电几次，看读数落在哪一侧
   —— 这条直接决定 S4/S5 里"上电位姿选哪、0 位放哪"（我们建议 0 位离边界 ≥10°）。

**验收**：实机记录表**统一在** [`runbook.md`](runbook.md) §5（S2a–S2f 与其余阶段在同一张表里，一次填完）：

| 子步骤 | 结论（判定依据见本 § 各条） |
|---|---|
| S2a 手转读数 | 连续？与手转方向一致？0 超时？ |
| S2b 读数形态 | 里程计 / 锯齿？ |
| S2c 反向跨零点 | 对称？有无整间隔跳变？ |
| S2d kd 扫描 | 误差 ∝ 1/kd？（加分项，不挡主线） |
| S2e 断链 | ✅ **不卸力**：继续执行最后一条指令；断电重上电后停止（2026-09-29） |
| S2f 上电基准 | 每次相同 / 差一个区间？边界多近会认错？ |

> S2d（kd 扫描、§3.6 末尾那个 0.034 圈/s 误差）是**加分项**：它不影响 S3–S5 的实现，
> 别让它挡住主线。S2b/S2c 里"正转跨零点连续"其实 S1 已经证过（§3.6：位置差分的速度 100.5% 稳定、

### 3.8 S3–S5 上机手册（`motor_ctl`：回归 0 / 键盘给角度 / 标零点 / 零点跳变）

程序：[`../apps/motor_ctl.cpp`](../apps/motor_ctl.cpp)（编译见 [`../README.md`](../README.md) §0，
用法与键盘命令表见 §6）。**先跑 §6 的 dry run 那四条**，确认程序本身没问题，实机时间只花在真事上。

```bash
cd ..            # 仓库根目录
B=@20260927_motor/cpp_part2/build/motor_ctl
sudo $B --port /dev/ttyUSB0 --id 0                 # 交互：h 看命令，先别急着给目标
```

**S3（任务书 2：回归 0 + 键盘给角度）**

1. 启动时程序先发一帧零力矩读位置，并把"当前位置"当成目标（**不会一上来就蹿**）；打印里会写
   `q_enc`（板子读数）、`offset`、`q`、以及"要转多少度、直线时间多少秒"。
2. 敲 `0` ⇒ 梯形插值（默认 90°/s、180°/s²）慢慢转回板子读数的 0 位。**这一步可能是多圈**（读数从上电起累计），
   多圈时程序会警告，确认输出端周围没人、线不会绕。
3. 敲 `30`（或任意角度）⇒ 转过去；到位后程序打印"到位（|差| ≤ 1.0°），保持中"。
4. 用记号笔/贴纸在**输出端**标下 0 位那一点；`mark` 记下它在软件里的坐标（会打出 `q` 与 `q_enc`，都抄下来）。

**S4（任务书 3：标零点 + 正向偏移 30°）**

1. （记号笔那个点就是"0 位"）敲 `o+30` ⇒ `offset` +30°，**电机不动**，记号笔那点读数变成 **+30.00°**
   —— 这就是"正向偏移 30°"的验收（"输出加、输入减"）。
2. 再敲 S3 里的那个目标角度（比如 `30`）⇒ 电机应**回到记号笔那一点**（相对上次的位置朝反方向少转 30°），
   读数仍等于目标角。`expect` 这时应报"≈0，零点没跳变"（它比的是 q 与记录值）。
3. 把 `offset` 记下来（`p` 会打），下次可以直接 `--offset-deg 30` 启动。

**S5（任务书 4：零点跳变）**

1. 用手把输出端慢慢转过记号笔那一点（**前后各试**，慢一点：一帧最多 2°）；跨过"编码器零点"（= 每个
   56.842° 的候选零点）时盯着终端：如果读数**跳一个区间**，程序会立刻打印
   `**零点跳变：pos 差 ±32768 …**` 并自动把 `offset` 补回去，电机不会跑偏。
2. 更接近任务书原文的做法：`stop`（卸力）→ 手转到零点附近（读数会很接近 0）→ 敲 `0` 或 `goto-mark`，
   看它是不是稳稳转回记号笔那一点、没有"跳变后跑到别处"。
3. 上电检查：下次上电先别动，`--expect-deg <记号笔那点的 q>`（或先 `stop` + `expect`）——
   差 ≈1 个区间就是"认错零点"（讲义 §2.6），程序默认会自动 `fix`，也可以加 `--no-fix-startup` 只看报告。

**dry run 已经验证过的**（证据：[`../../output/terminal/motor-ctl-dryrun-20260929.txt`](../../output/terminal/motor-ctl-dryrun-20260929.txt)（tick 版；09-28 那份是 float 版），复现命令见 [`../README.md`](../README.md) §6）

| S5 上电认错零点 | `--fake-datum-turns 1 --expect-deg 0` | 启动检查报"差了 +1 个零点区间"⇒ 自动 `offset −56.842°`（= −32768 tick），**板子读数不变、电机不动** |
| S5 运行中跳变 | `--fake-jump-frame 40 --fake-jump-turns ±1 --script "60"` | 第 39 帧报 `pos 差 ±32768`，`offset` 补 ∓1 个区间；**物理目标没变**（B1 末位置 60.009°、B2 末位置 30.010°） |
| S5 锯齿读数 | `--fake-sawtooth --script "100"` | 每跨一个区间报一次"跳变"并补回 ⇒ 同一套修正逻辑顺带把"锯齿"变成"里程计"，末位置 100.009° |

两条 dry run 里学到的、**写代码时踩过的**坑（都已固化进程序）：

* offset 一变，**同一帧**里必须让"报文里的目标"跟着变：`q_des` 与 `offset` 同向挪 ⇒ `(q_des − offset)` 不变
  ⇒ 物理目标不变。只挪一半会让驱动板按 56.842° 的位置误差使劲（第一版实测力矩峰值冲到 **41.8 N·m**，
  修好后 0.5 N·m）；
* 跳变修正**只能改 `offset`**，不能顺手挪 `q_des`：前者让"同一个 `q_des` 仍对应同一个物理位置"，
  后者会把物理目标整段挪一个区间（dry run 里实测多了 56.842°）。

> 假电机的等效惯量（`J = 1e-3`）比真机小得多，所以"跳变那一帧驱动板自己抡一下"的**幅度**在 dry run 里
> 是被放大的（力矩峰值本身可信：`τ = K_P × 位置误差 ≈ 1.9966 × 6.283 = 12.5 N·m` 转子侧）。

## 4 需要先确认的事（问老队员 / 量一下）

1. **转接头是 TTL 还是 RS485**：这颗 FT232H 出来的是 TTL 串口（TX/RX/GND），如果电机侧要差分 A/B，
   中间得有一个 TTL↔RS485 收发器（板上有没有 MAX485/SP3485 之类的芯片？四根线还是两根线？）。任务书说
   "小白接线请求助四足/电控老队员"，这条最该先问清。
2. **电机 ID**（出厂 0？有没有用 `changeID` 例程改过），以及是不是**单电机**接到这条串口上。
3. **电源**：大疆电池多少 V、要不要限流、电机与转接头**是否共地**。
4. **机械保护**：电机固定好了吗、输出端有没有负载/夹具（S1 会被电机带着转，S3–S5 用手转输出端找零点）。

> 与**数值/精度**有关的量（编码器重复性/背隙、减速比到底是 6.33 还是 19:3、长会话的浮点漂移、
> 反馈包头字节等）不在这四条里，按"先累积、上机再测"的方式记在 [`fixed_point.md`](fixed_point.md) §6 的清单里。

## 5 零点标定与“跨零点”的约定（讲义 §2.4–2.6 ↔ 我们的代码）

### 5.1 四个量

| 符号 | 含义 |
|---|---|
| `p` | 驱动板报出来的**转子侧**角度（`data.q`，rad；报文里是 int32 q15 圈的定点） |
| `q_enc = p / N` | 换算到输出端、**还没加偏移**的读数 |
| `offset` | 软件偏移量（就是标定时要“录进去”的那个数）；含“上电落在哪个零点”的修正 |
| `q` | 我们（关节侧）对外用的角度 |

### 5.2 偏移的写法：**收到加、下发减**（讲义 §2.5）

```
q     = q_enc + offset              // 收到（读回来的）加偏移
cmd.q = (q_des - offset) * N        // 下发（要发出去的目标）减偏移，再换到转子侧
```

两个方向**必须反号**。课程视频里是同一件事的另一种记法（“输入减、输出加”），那只是把 `offset`
取相反的符号；**闭环行为完全一样，但两个方向写成同号就变成正反馈**（一给目标就飞）。
所以代码里建议只存一个 `offset`，两个方向分别 `+`/`-`（本仓库的 §5.2 就是这种）。

### 5.3 “正向偏移 30°”怎么录（定符号的唯一标准）

不要靠记符号，靠这个测验：**标定前**记号笔那个点就是我们的零点（即那里 `q_enc` 对应 `q = 0`）；
标定后**同一个物理点**必须读 **+30°**：

```
offset_new = offset_old + 30°    // §5.2 的写法（收到加）：想让标记点读数变大 ⇒ offset 变大
```

（若用视频那种“输入减、输出加”的写法，同一件事就是 `offset_new = offset_old - 30°`。）
**验收**：不动电机、只改 `offset`，终端读数应该从 0 变成 **+30.00°**，而输出端一根线都没动；
之后再让电机去 S3 那个目标角度，它应该**朝反方向少转 30°**就到位（因为零点往前挪了 30°）。

### 5.4 两种“跨零点”，别搞混

| 情况 | 现象 | 处理（`motor_ctl` 里的实现） |
|---|---|---|
| **正常跨零点**（转着转着越过一个候选零点，输出端每 56.842° 一次） | 驱动板维护**里程计**时：读数连续，什么都不用做（S1 实测正转就是这样）；只报**相对最近零点**时：读数从 ~56.842° 掉回 0°（锯齿） | **两者现在用同一段代码处理**：锯齿的每一次"掉回"都表现为 raw 差 ≈ −32768（= −1 个区间），被下面那条判据抓到后把 `offset` 补 +1 个区间 ⇒ 等价于"自己数跨过了几个零点"；里程计那种根本不触发，`offset` 一直不动 |
| **上电落在别的候选零点**（"认错零点"，讲义 §2.6）——**这是主线**；运行中的整圈跳变只作**兜底**（§2 见 [`zero_semantics.md`](zero_semantics.md)） | 整体平移一个区间：同一物理位置，这次读数比上次大/小 ≈ 56.842°（输出端）；运行中若出现，表现为一帧里跳 ≈1 个区间（异常） | 判据用**整数**：`Δ(pos raw)` 恰好是 `k × 32768`（k 个转子圈 = k×56.842° 输出端；残差只用来容忍"跳变那一帧驱动板自己的位移"），比"角度百分比"稳；判定成立就**只把 `offset` 反向补 k 个区间**（`q_des` 不动）——报文目标 `q_des − offset` 自动跟着挪 k 个区间，正好抵消板子基准的漂移 ⇒ **同一个 `q_des` 仍对应同一个物理位置**；上电那一次用 `--expect-deg`/`expect` 提前发现并自动修 |

> 修正时**不能**顺手挪 `q_des`/`q_cmd`：那等于把物理目标整体挪一个区间（dry run 里实测多转了 56.842°）。
> 判据的残差容差要 **远大于**"正常最高转速 × 真实帧周期"（1 圈/s × 5.585 ms ≈ 2°；跳变那一帧驱动板
> 自己还会多走 ~3°），又要 **远小于** 半个区间（28.4°）——默认 8°。
>
> §3.8 末尾的 dry run 表就是验证这几种情形的：`--fake-datum-turns`（上电落在别的候选零点，**主线**）、
> `--fake-jump-frame`（运行中换基准，正反两个方向，兜底）、`--fake-sawtooth`（锯齿，兜底）。
>
