# 项目约定

本文是本仓库的**全量约定**，读者是在这里写代码、写文档的人，以及 AI 助手。AI 助手另有一份简版 [`AGENTS.md`](../AGENTS.md)：动手前必须知道的要点，加上只对助手成立的规则（开始时读什么、不代为提交、署名、改写历史）。两份互不重复：细则只写在本文，`AGENTS.md` 只放一句话加指向本文的指针。

## 读法与适用范围

- **用词**：规则句默认是硬性要求（照做 / 不要做）；带「应」「建议」的是默认做法，有理由时可以不照做；带「可」的是允许的做法。
- **结构**：每条以加粗的一句规则开头，照做时读这一句就够；下面按需附「理由」「判定」「例」「例外」「历史」。
- **编号**：条目编号为「节.条」，引用时写 `conventions §2.6`。§1–§8 的节号已被全仓引用，不要重排；新条目加在所属节的末尾，删掉的条目编号空着、不挪用。
- **适用范围**：本文约束**新任务**与**正在重写的部分**。既有任务里与现行约定不同的写法（C++ 格式、XML 注释等）保持原样、不回改；某个既有工程整体重构时再一并对齐。下文的"既有任务保留现状"都是这一条的具体情形。
  - 理由：那些文件与已记录的实测、复现步骤绑在一起，回改会让"复现"和"当时的文件"对不上。
- **来源**：验收规范（`四足组培训任务提交与验收规范.md`，本机只读材料，下文写作"验收规范 §N"）、对提交方式的明确要求、以及踩坑后写进 [`pitfalls/environment.md`](pitfalls/environment.md) 的经验。
- **维护**：改约定时改本文；`AGENTS.md` 里有对应那句话的，一并改掉。
- 开新任务从 [§8 起步清单](#8-新任务起步清单) 开始。

## 1. 提交信息（commit message）

- **1.1 提交信息只写一行英文，不写正文。** "这次做了什么、做到哪一步"由仓库里的文档体现。
- **1.2 格式为 `type(scope): 一句话`。** `type` 取 `feat` / `fix` / `docs` / `refactor` / `build` / `chore` / `test`；`scope` 可省略。
  - 例：`feat(cpp): add dog_sim (toolchain, model load, rest-pose check)`、`docs: explain why pixi is used`。
  - 历史：更早的提交用过 `work:` 前缀（如 `work: training02 task 2 done`），新提交不再用。
- **1.3 分阶段提交，不攒到最后一次**（验收规范 §3.1）：搭环境 / 加载模型 / 加控制 / 整理结构 / 补文档分别提交。

AI 助手专属的提交规则（不代为提交、不写署名、改写已推送历史的做法）见 [`AGENTS.md`](../AGENTS.md)「提交」。

## 2. 文档

### 排版

- **2.1 Markdown 每段写成一行。** 一个段落（含列表项、引用块里的段落）不按宽度硬折行，在编辑器里开 word wrap 看；代码围栏、表格、目录树原样保留。
  - 理由：渲染器把软换行当成空格，中文里会凭空多出一个空格；一行一个完整段落，按行检索更自足，改一句话 diff 也只动一行。
  - 例外：讲义 / 任务书这类**转录件**（放在任务目录的 `docs/teaching-materials/`，如 `@20260927_motor/docs/teaching-materials/`）保持原样，不参与排版归一。
- **2.2 表格单元格里的竖线写成 `\|`**（绝对值、或运算等，如 `\|τ\| < 死区`）；写在行内代码里也要转义（`` `\|τ\|` ``）。
  - 理由：不转义会被当成列分隔符，渲染成错列。`&#124;` 也能用，但更难读。
  - 检查：`check_md_links.py`（§2.12）会按竖线数报出这类错误。
- **2.3 图示可用 ASCII 或 Mermaid，按表达力选。** 小的、两行内能说清的流程 / 数据流用 ASCII（读得懂即可）；纯文本两行说不清、宽到在非等宽字体下可能错位、或是时序图 / 甘特图 / 状态机这类 Mermaid 有专门写法的，用 Mermaid（能被自动渲染）。

### 入口与进度

- **2.4 每个正式任务目录都有一份 `README.md`**，至少写明：做了什么、环境与依赖、如何编译或运行、主要文件与目录的作用（验收规范 §4.2）。
  - "正式任务目录"指培训任务书对应的那一级 `@<日期>_<主题>/`。它内部的练习工程、示例工程不算，按需写或不写 README。
- **2.5 README 只做入口。** 任务 README 写：做了什么、怎么跑、结果在哪、细节往哪跳；根 README 写：定位、任务记录、快速开始、文档索引。具体内容与长的操作步骤放 `docs/`。
- **2.6 README 不记进度。** 完成到哪、TODO、下一步、阻滞项、提交 / 分支情况（如有）写在任务目录的 `docs/status.md`，README 只留一个指针。
  - 判定：问"这条内容在当前 TODO 做完后 / 下周 / 任务完成时还成立吗？"——成立的留在 README；不成立的（打勾、日期、"已完成 / 待做"）放 `docs/status.md`。
  - 理由：进度是会变的内容。混进入口文档后，每次推进都要改 README，"怎么建、怎么跑、文件干什么"这些不变的内容反而被埋掉；分开后，README 只在结构变化（增删文件、改用法）时才动。

### 存放

- **2.7 仓库 `docs/` 按类别分子目录，根下只留本文。** 当前类别是 `learn/`（研究与学习）、`pitfalls/`（踩坑记录），类别可增删改。什么内容进仓库 `docs/`、什么留在任务目录，见 §7。
- **2.8 任务目录的 `docs/` 可平铺。** 靠文件名成组、靠各级 README 的索引表检索；单目录超过约 15 篇，或出现清晰的主题簇时，再分子目录。
- **2.9 配置文件里的注释引用文档，不重复结论。** 例：`pixi.toml` 的注释只写"见 `docs/pitfalls/environment.md` 某节"，"为什么"留在文档里。

### 路径与链接

- **2.10 文档里出现的路径、目录树必须与仓库实际一致。** "文档写了但仓库里没有"同样算错。
- **2.11 移动 / 重命名文档时，全仓搜一遍指向它的引用**（文档、代码与配置注释），把对方那一侧一并改对。新增引用时让双向链接成对：对方没有合适的位置，就在它的首部或尾部放一个反向链接。
- **2.12 改完文档要自检**：代码围栏是否配对、相对链接与锚点是否有效、双向引用是否成对、目录树是否与实际一致。链接、锚点与表格列数可以自动查（从仓库根执行）：`pixi run python @20260927_motor/scripts/agent_scripts/check_md_links.py <目录>`；其余几项人工对照。

## 3. 目录、命名与代码格式

### 任务目录

- **3.1 任务目录名为 `@<日期>_<主题>`。** 与验收规范建议的 `01_/02_…` 序号方式等价；全部任务与目录的对应关系只记在根 [`README.md`](../README.md) 的「任务记录」，本文不另列。
- **3.2 层级统一叫「培训 → 任务 → 子任务项」，编号与名字照任务书原文。** 不要自造"第 N 部分"这类编号。
  - 例：培训"第三次培训" → 任务 `@20260927_motor`（关节电机）→ "子任务项一（仿真部分）"（`cpp/`）、"子任务项二（实体电机控制）"（`cpp_part2_remake/`，历史版本 `cpp_part2/`）。
  - 历史：旧文档里出现过与任务书不一致的"第三部分"，已统一。

### 命名与布局

- **3.3 程序侧用下划线，文档侧用连字符**，按下表取名。顶层任务目录名 `@<日期>_<主题>` 是固定格式，不受本条约束。
  - 历史：早期约定"一律下划线"，2026-09-29 改成下表的口径，当时把 3 份文档（`zero-semantics.md` / `fixed-point.md` / `fake-motor.md`）从下划线改成连字符；代码与脚本本来就没用连字符。

| 对象 | 写法 | 例 |
|---|---|---|
| 程序 / 脚本，及它们所在的目录 | 下划线 | `agent_scripts/`、`onetime_tools/`、`run_log.sh`、`search_stance.cpp` |
| 文档（`.md`），及文档所在的目录 | 连字符 | `docs/learn/runtime-timing.md`、`@20260927_motor/docs/teaching-materials/`、`@20260927_motor/cpp_part2/docs/zero-semantics.md` |
| 其余（产物、日志、分支等） | 应优先用连字符；§3.4 的产物名 `<状态>_<动作>` 例外 | `motor-real-202609291655-s1a.txt` |
| 平台 / 工具规定的名字 | 照原样 | `.github/copilot-instructions.md`、`.clang-format`、`pixi.toml` |

- **3.4 任务目录按语言分子目录**，布局见下方模板（按需取用，不是某个任务的实际目录）。
  - 产物命名：结果导向、两侧同名，格式 `<状态>_<动作>`，如 `rest_down`（趴卧）、`stand_up`（起身）、`slope_stand`（斜面站住）；分辨率或帧率另加后缀，如 `_1080p120fps`。C++ 与 Python 做同一件事的产物用同一个名字；默认输出路径写在产出脚本里。

```text
@<日期>_<主题>/
├── README.md                 # 入口（§2.4、§2.5）
├── docs/                     # 细节文档；进度在 docs/status.md（§2.6）
├── assets/ models/ scenes/   # 语言无关的资源
├── python/                   # 仿真与可视化代码
├── cpp/                      # C++ 工程
├── ws/src/<包>/              # ROS 2 包（§3.5）
├── scripts/                  # 人跑的一次性工具（§3.6）
│   └── agent_scripts/        # AI / 自检用的诊断脚本（§3.6）
└── output/<语言>/            # 产物（建议），如 output/python/、output/cpp/
```

- **3.5 ROS 2 任务的 colcon 工作空间放 `<任务>/ws/`，包放 `ws/src/<包>/`**（参考 [`../@20261005_ros2/ws/src/quadruped_ros2/`](../@20261005_ros2/ws/src/quadruped_ros2/)）。加新任务不必改根目录的文件：`pixi run ros2-build` 按 `<任务目录>/**/src/<包>/package.xml` 自动发现并编译（[`../scripts/build_ros2_workspaces.sh`](../scripts/build_ros2_workspaces.sh)），激活环境时再自动 source 已构建的 `install/`（[`../scripts/activate_ros2_workspaces.sh`](../scripts/activate_ros2_workspaces.sh)）。
  - colcon 会把 `ws/` 下每个带 `package.xml` 的目录都当成要编的包：移植外部工程时只拷用得到的包，不要把整棵上游树（连同它的仿真器插件、第三方 SDK）放进 `src/`。
  - 新任务的包**可以依赖前面任务的包**（如 `@20261007_assignment` 的 `rl_sar` 用 `@20261005_ros2` 的消息）：`ros2-build` 按目录名（即日期）顺序编译，每编完一个工作空间就 source 它，所以后面的能找到前面的；反过来不行。在 `package.xml` 里写上依赖，在任务 README 里写明依赖哪个任务。

### 脚本与入库

- **3.6 脚本按"谁来跑"放。** `<任务>/scripts/agent_scripts/` 放 AI / 自检用的诊断脚本（像素无关的自动判定、参数扫描、日志分析）；`<任务>/scripts/` 放人跑的一次性工具（如要 `sudo` 的 `setup_joy_devices.sh`）。
- **3.7 为一次调查服务的仪器不进主干代码。** 计时、截图、临时开关与环境变量开关，调查完要么删掉，要么搬进 `agent_scripts/`；主干里只留人也会看的诊断（启动打印、状态行、`--self-test`）。
  - 判定：问"这条输出 / 这段代码，验收现场的人会看吗？"——不看就搬走。
- **3.8 构建产物、缓存、大二进制不入库**（验收规范 §4.4）。`.gitignore` 已覆盖 `build/`、`install/`、`log/`、`.cache/`、`__pycache__/`、`.pixi/` 等；重复的大资源用软链接共用一份真实文件。

### 代码格式

- **3.9 C/C++ 与 CMake 用 4 空格缩进，不用 Tab。** 仓库根的 [`.clang-format`](../.clang-format)（`IndentWidth: 4`、`ColumnLimit: 0` 即不自动折行）是默认配置；格式化用 `clang-format -i <file>`，它会用离文件最近的那份 `.clang-format`。
  - 用**环境里的** clang-format（`pixi run clang-format -i <file>`，或激活环境后直接用），与编辑器（环境里的 clangd）同一版本；系统 apt 的 14 版结果不同（差在行尾注释的对齐），见 [`pitfalls/environment.md`](pitfalls/environment.md)「系统的 clangd 14 读不了 gcc 15 的头」。
- **3.10 新任务的 C++ 工程用新格式：C++17 + Allman 大括号 + 100 列。** 在工程目录放一份自己的 `.clang-format`（照 [`../@20260927_motor/cpp_part2_remake/.clang-format`](../@20260927_motor/cpp_part2_remake/.clang-format) 复制），并在注释里写明"本目录采用 100 列"。
  - 参考：[`../@20260927_motor/cpp_part2_remake/`](../@20260927_motor/cpp_part2_remake/README.md)（现行）、[`learn/cpp-cmake.md`](learn/cpp-cmake.md) 的「工程目录与文件风格」一节；当时的拆分理由在历史版本 [`../@20260927_motor/cpp_part2/docs/setup.md`](../@20260927_motor/cpp_part2/docs/setup.md) §1。
  - 既有工程（`@20260923_mujoco/cpp_*`、`@20260927_motor/cpp/`）保留现状（见「适用范围」），等各自的结构对齐时一并切换。
- **3.11 XML / MJCF 注释里不要出现 `--`。** 要提命令行开关时换个说法（"pitch/roll 参数"），别把 `--pitch` 原样抄进注释。
  - 理由：XML 规范禁止注释内出现双连字符。MuJoCo 用的 tinyxml2 很宽松（连 `--->` 都读得进去），但 `xml.etree`、`xmllint` 这类严格解析器会直接报 `not well-formed`，编辑器与外部工具也会报警。
  - 实测（`@20261005_ros2` 的两个 xml，记录在该任务 `docs/status.md`）：5 种写法在 MuJoCo 3.12 下全部读得进去（`nq=19 ngeom=50` 不变），ElementTree 全部报错；改完后两边都通过。
  - 既有任务（`@20260923_mujoco`、`@20260927_motor`）里的同类写法保持原样（见「适用范围」）。
- **3.12 连续物理量用国际制单位（SI）；非 SI 的量在名字里带后缀。** 长度用米、时间用秒、角用弧度、力矩用 N·m（增益 N·m/rad、N·m·s/rad），代码、配置、消息、文档同一个口径；确实要用度或毫秒时把单位写进名字（`tilt_warn_deg`、`TiltDeg()`、`--period-ms`），日志 / 表格的表头也写单位。
  - 理由：SI 之外没有第二个"默认"——名字不带单位后缀就按 SI 读；带后缀的量一眼能认出来，不会在跨节点、跨语言的接口上把度当弧度用。
  - 判定：看到 `tilt`、`q`、`dt` 这类没后缀的名字先按 SI 理解；发现某个量确实不是 SI 时，改名加后缀（`_deg` / `_ms`），而不是只在注释里说明。
  - 例：`q` / `dq` [rad、rad/s]、MIT 的 kp / kd [N·m/rad、N·m·s/rad]（[`../@20261005_ros2/ws/src/quadruped_ros2/msg/MitCommand.msg`](../@20261005_ros2/ws/src/quadruped_ros2/msg/MitCommand.msg)）；用度的都带后缀：`tilt_warn_deg`、`quadruped::attitude::TiltDeg()`、诊断脚本的 `--period-ms` / `--delay-ms`。yaml / 配置字段的单位在本任务文档里列成表，如 [`../@20261007_assignment/docs/porting.md`](../@20261007_assignment/docs/porting.md) §3.1。
  - 例外：逐字 / 整体复制的外部代码按原样保留（§6.2、「适用范围」），如 rl_sar 框架层 `library/core/rl_sdk/rl_sdk.cpp:228` 的 `AttitudeProtect()`（阈值按度用、名字没后缀；本移植里没人调用它）。

## 4. 环境与依赖

### 环境

- **4.1 全仓只有一个环境：根 `pixi.toml` + `pixi.lock`。** Python / C++ / MuJoCo / ROS 2 的依赖都声明在这里，命令一律 `pixi run …`；不为新任务另开环境。
- **4.2 加依赖只改根 `pixi.toml`**（`pixi add <包>`，或手改后 `pixi lock`），`pixi.lock` 与它在同一次提交里。
  - 包从已配置的通道（`robostack-humble`、`conda-forge`）取；不用 `sudo apt`，不依赖系统 `/opt/ros`。
  - 每个新依赖在 `pixi.toml` 里留一行注释，说明谁用、为什么；理由长的写进文档，注释只放指针（§2.9）。
- **4.3 C++ 与 Python 用同一个 MuJoCo 版本**（当前 3.12.0）。
- **4.4 必须在进程早期生效的环境变量写进 `[activation.env]`**（如 `MUJOCO_GL`）。
- **4.5 环境为什么这样选，只写在 [`pitfalls/environment.md`](pitfalls/environment.md)**；任务 README 只写怎么用。

### 路径

- **4.6 代码、脚本、配置里不写死绝对路径**，尤其是本机家目录（`/home/<用户名>/…`）；用相对路径、环境变量或命令行参数（验收规范 §9：环境相关参数不硬编码）。
  - 理由：绝对路径泄漏本机目录布局，换台机器就复现不了，验收时也是冗余信息。
  - 文档里的示例命令可以用 `/tmp/…`（临时产物）或"从仓库根执行"的相对路径；确实要展示某台机器上的实际路径时，写明它只是示例。
- **4.7 仓库之外的路径一律不写进同步内容**（文档、注释、命令、配置、代码都算），如 `../ReadOnly.d/…`、`../../../Replicate.d/…`、`/home/…/Replicate.d/…`。
  - 理由：同 §4.6；而且那些材料根本不在仓库里，别人 clone 后照着也找不到。
  - 引用只读材料（`ReadOnly.d` 下的任务书、讲义、`unitree_actuator_sdk`、`unitree_mujoco`、`quadruped_control` 等）只写名字或相关内容，如 `` `ros2任务.pdf.md`（本机只读材料） ``、`` `ReadOnly.d/unitree_actuator_sdk` ``、`` `quadruped_control/configs/input/gamepads.yaml`（只读材料里） ``。只读材料不进版本库，不存在要维护双向链接的问题，写名字就够了。
  - 命令里确实要用那个路径时，用变量或占位符（`$UNITREE_SDK_DIR`、`<只读材料里的 unitree_mujoco>`）。
- **4.8 程序确实要用仓库之外的资源时**（如实体电机工程要链宇树 SDK），路径由本机、不入库的 `local_paths.cmake` 提供；仓库里只留这个机制，不留任何具体路径。
  - 模板 [`../local_paths.cmake.example`](../local_paths.cmake.example) 入库，真实文件在 `.gitignore` 里；工程同时接受命令行 `-D<变量>=<路径>` 与环境变量，命令行优先。机制的完整说明只写在模板里（§4.9）。

### 复现

- **4.9 复现步骤前面先写"先怎么准备"。** 凡是用到仓库里没有的东西（`local_paths.cmake` 里的本机路径、只读材料的位置），先写一句准备步骤（如 `cp local_paths.cmake.example local_paths.cmake` 后填好），并让它与命令里用的变量一致：命令里用 `$(sed -n 's/^set(UNITREE_SDK_DIR "\(.*\)")$/\1/p' local_paths.cmake)` 取值，不在文档里再写第二处路径。
  - 机制的解释只写一处（`local_paths.cmake.example`），各 README / 任务文档只放一行指针（单一信息源，同 §7.1）。
- **4.10 要复现者自己准备的外部资源，写明来源。** 上游仓库给 `git clone <URL>`（重要时补 commit / 版本，如 `unitree_mujoco` 的 `1eb6642`），官方发布包给下载页与版本（如 MuJoCo 3.12.0 的 release 包）。命令要能照着敲通；不能默认读者手上有那份只读材料，也不能只写"按上游说明来"。

## 5. 验证与证据

- **5.1 每个结论都给可复现命令与实测数字**，不写"感觉更快"这类表述。
- **5.2 度量前先把被测对象隔离出来。** 先做开 / 关对照（如开阴影、关阴影两帧相减）或用掩膜限定区域（如分割渲染只取地面像素），再量化；并拿一个"已知正确"的参考实现做基准。
  - 理由：整图 / 全局指标会被无关内容淹没。
  - 例：用"整图相邻像素梯度 > 120 的像素数"量阴影画质时，1 px 的 HUD 白字（对比度 255）主导了计数，而地面上阴影 / 受光的反差够不到阈值，结果同一画面在明显更糙和更细的配置下读数几乎一样。
- **5.3 引用外部代码或仓库时给可核对的位置**（`文件:行`，如 `simulate/src/main.cc:413`），不要只写"在 main.cc 里"；结论性说法要能顺着这个位置查到。
- **5.4 改了代码 / 脚本就跑对应的回归**：任务 `scripts/agent_scripts/` 下的诊断脚本，以及 C++ 程序的 `--self-test` 这类不接硬件就能跑的自检；结果与当前状态记进任务的 `docs/status.md`（不写进 README，§2.6）。
- **5.5 同一份输入、两种实现，做逐项对照。** 替换某一层（换控制器、换仿真）时，先让新旧两版在同一份模型、同一组输入下给出能对照的数字。
  - 例：`@20260923_mujoco` 的 C++ 复刻与 Python 共用同一份 MJCF；`@20261005_ros2` 移植第三次培训的控制核心后，两边末态 z 都是 0.3836 m。

## 6. 外部代码与许可

- **6.1 用到外部代码或资料时，在所在任务的 README 里写明来源**：上游名称、URL、版本或 commit、许可证（验收规范 §8）。目前用到的有 `unitreerobotics/unitree_mujoco`（BSD-3-Clause）与 MuJoCo 官方示例（Apache-2.0）。
- **6.2 移植 / 改写外部工程（不只是参考）时，保留原文件的版权与许可头。** Apache-2.0 的代码还要随附许可证文本，并在改过的文件里写明"已修改"（Apache-2.0 第 4 条）；上游 URL + commit 写进任务 README，便于对照改了哪些。
- **6.3 只拷用得到的文件。** 不把整个上游仓库（含第三方 SDK、预编译库）搬进来。
- **6.4 不整段照搬。** 验收会要求现场解释并按需小幅修改自己的代码（验收规范 §6），所以结构要小而清楚。

## 7. 文档职责分工（任务目录 vs 仓库 `docs/`）

- **7.1 写之前先问"换个任务还成立吗？"** 成立 → 写进仓库 `docs/`；只对这份模型 / 这次验收成立 → 写在任务目录。同一条内容只写一处，其他地方放指针。
- **7.2 仓库 `docs/` 写跨任务成立的东西**：MuJoCo 知识点与坑点、图形栈、编辑器提示、环境 / 镜像 / 工具链的依据，以及换个任务也成立的通用踩坑（如 `<include>` 后 `meshdir` 的解析规则、keyframe 不会自动加载）。环境类结论与数字（工具链怎么配、图形后端、镜像、显卡与渲染开销）集中在 [`pitfalls/environment.md`](pitfalls/environment.md) 与 `learn/`。
- **7.3 任务目录写只对本任务成立的东西**：模型来源与转换取舍、本任务的过程与产出、运行方式与结论表、只对这份模型成立的数字，以及推进情况（`docs/status.md`：阶段状态、下一步、阻滞项、提交与分支）。本任务自己的实测数字留在任务目录，哪怕是在本机上测的时间、温度、力矩，也不必搬到仓库 `docs/`。
- **7.4 分层样例**：[`../@20260923_mujoco/`](../@20260923_mujoco/README.md)（README 入口 + `docs/` 下分篇；通用部分放在 `docs/learn/mujoco.md`、`docs/pitfalls/environment.md`，任务里只留结论 + 指针）、[`../@20261005_ros2/`](../@20261005_ros2/README.md)（README 入口 + `docs/` 下按主题分篇，进度在 `docs/status.md`）。新任务沿用这个分层。

## 8. 新任务起步清单

开新任务时按顺序过一遍；每步的细则在括号里的条目。

1. 建目录 `@<日期>_<主题>/`（§3.1），放 `README.md`（§2.4、§2.5）与 `docs/status.md`（§2.6）；在根 [`README.md`](../README.md) 的「任务记录」加一行。
2. 只读材料（任务书、讲义）只写名字、不写本机路径（§4.7）；程序确实要用仓库之外的资源时，走 `local_paths.cmake`（§4.8）。
3. 新依赖加进根 `pixi.toml`，和 `pixi.lock` 一起提交（§4.2）。
4. 代码按 §3.4 摆放：C++ 工程用新格式（§3.10），ROS 2 包放 `ws/src/`（§3.5），诊断脚本放 `scripts/agent_scripts/`（§3.6）。
5. 用到外部代码时先记来源与许可，移植时保留版权头（§6.1、§6.2）。
6. 每次提交前：跑对应自检并更新 `docs/status.md`（§5.4）；改过文档就跑 `check_md_links.py`（§2.12）；提交信息按 §1 写，分阶段提交（§1.3）。
